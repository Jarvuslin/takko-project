    assetPipeline entry  needId=punchAnim  status=passed  component=yes
    destinationPath      Workspace/Forge_8a81efe9b8ed/Assets/punchAnim

The content is IN THE PLACE, inside the generated namespace. The generated code wrote:

    local PUNCH_ANIMATION_ID = "rbxassetid://12061946559"

That is the PACK asset id, for content that was already retained locally. It reached
across the network for something sitting in its own folder. Animator:LoadAnimation will
fail on it.

Worse, the model UNDERSTOOD the correct path and did not take it. Its own comment says
the Studio-only temporary registration id "plays correctly for in-Studio testing". It
then produced publishing-shaped code anyway and labelled it an unmet dependency. The
comment claim that "the wiring below is correct" is FALSE for the Studio path it was
told to target.

Root cause: the builder receives animationCapabilityContract as prose describing
options, with a prominent publishedGame:"unsupported" and a limitation field. The model
weighed the limitation and hedged. It was never plainly told (a) where the retained
content is, (b) that a Studio place is this product's actual deliverable, or (c) the
exact pattern to emit.

Changes:

  a) TELL THE BUILDER WHERE THE CONTENT IS. When a need has a retained component, pass
     its destinationPath and rootName into the builder task context as local content.
     Retained assets must be referenced in-place, never re-fetched by asset id.

  b) SUPPLY THE EXACT PATTERN, NOT A DESCRIPTION. For a retained raw KeyframeSequence,
     give the concrete integration shape: locate the sequence under the component root,
     KeyframeSequenceProvider:RegisterKeyframeSequence(sequence), assign the returned
     string UNCHANGED to Animation.AnimationId (no rbxassetid:// prefix, no hash://
     prefix), then Animator:LoadAnimation. The native probe proved this plays, with
     0.98 rad of real joint motion, ordinary Script and LocalScript, server and client.

  c) STATE THE TARGET. Takko delivers a Studio place for testing. Studio-local playback
     is the SUPPORTED path for generated code. The publishing limitation is a
     project-level note for the user, not a reason for the builder to hedge or emit
     non-working wiring. Keep the limitation visible in requirement coverage, but stop
     presenting it to the builder as a blocker.

  d) MAKE IT CHECKABLE, not hopeful. Add a validation: if a need's retained component is
     a raw KeyframeSequence and generated code assigns "rbxassetid://<that pack id>" to
     an Animation.AnimationId, reject it in the correction callback with a message that
     names the file, the need and the retained destinationPath. This is the same
     principle as every other fix: verify the structured fact rather than trusting prose.

Do NOT add publishing. Do NOT invent an AnimationId. Do NOT special-case this asset,
this animation or fighting games. The rule is generic: retained component content is
referenced in place.
