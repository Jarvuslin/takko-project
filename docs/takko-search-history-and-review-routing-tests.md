# Search feedback and separate source review

Two measured failures motivated these changes. Required Marketplace workers could not see which queries had already failed, and the inexpensive component reviewer missed preservation/scope problems despite receiving both source versions. The [frozen Sol comparison](../research/results/component-preservation-sol-v1/RESULTS.md) detected those issues for9.2cents, with documented semantic qualifications.

The asset pipeline now includes a bounded chronological `searchHistory` in every decision context: search number, exact executed query, adapter-returned candidate count and offered count. These counts describe what Takko received after adapter filtering, not the whole Marketplace inventory. Each context gets its own copy. Successful search summaries are persisted, and generic guidance asks the worker to consider shorter common names or synonyms after empty results. The worker authors every query. Engine allows3searches instead of2; the3inspection budget is separate. Required acquisition, optional-visual sourcing evidence, audio restrictions, cancellation and unknown-effect guards are unchanged.

Settings optionally accept `routes.componentReviewer: [profileId]` for one configured profile. Empty/absent uses the usual reviewer, preserving old evidence hashes. Only initial and post-adaptation component-source reviews use this override. Audio/visual evaluation and ordinary game review retain the normal reviewer route. The full override profile participates in asset context hashes, so changing/removing it invalidates retained acceptance instead of silently reusing reviews from another configuration. Normal key/model preflight, strict validation, two format attempts, charge accounting and no implicit fallback remain. Profile creation/deletion in the settings UI preserves or removes optional route references correctly. This is API-configurable; no default model is forced or running app changed.

Focused tests exercise third-query success through normal visual and audio verification, all-empty required Model/Audio failure, duplicate/wrong-kind counts, context mutation isolation and repeated-query limits. Engine tests exercise both source-review stages, untouched visual/audio/general routes, unknown profile rejection, empty legacy fallback, retained-context invalidation, single-profile failure and charge/trace identities. Offline doubles do not prove Studio behavior or source-review quality.

The [fresh search diagnostic protocol](../research/results/search-history-v1/PROTOCOL.md) uses the original V9 course need and actual Marketplace responses, stopping before inspection. It measures discovery only, preserving the distinction between finding a candidate and proving a working game.

Full `npm run check`: **1,081 unit/API +10 desktop +36 browser tests**, all stages passed. The [live diagnostic](../research/results/search-history-v1/RESULTS.md) selected a returned candidate for1.9cents, but the original query now returned20 results on its first attempt. It therefore verifies real context delivery and raw selection, not better retry behavior or candidate fitness. No native mutation or live-app restart was performed.
