# Direct Studio delivery without manual export

2026-09-20. Recommend extending Takko's existing Studio plugin to receive retained native components directly. Manual place export can become an optional download rather than the normal delivery workflow. This is a source-backed design and offline feasibility audit, not an implemented or native-verified delivery feature.

The original assessment and offline evidence below are retained.

## What the user should experience

One **Roblox Studio** entry point. After initial setup, show the selected place and a single primary action: **Apply to Studio**. First-time setup explains installing the Takko plugin and allowing its local connection. Remember the preferred place, but require selection again when identity is ambiguous. Never silently target another open game.

The normal flow is:

1. Generate in Takko.
2. Click **Apply to Studio**.
3. See **Preparing**, **Transferring**, **Applying**, then **Ready to test**.
4. Click **Test game** when ready to start a playtest.

There should be no export picker, import dialog, command bar snippet, Rojo server or manual port field in the everyday workflow. Keep **Download a copy** in the overflow menu. Put session IDs, adapters, ports and versions under **Connection details**. A plugin update should have one clear instruction rather than a generic connection error.

For repeated use, offer explicit session trust during pairing: **Allow apply requests from this Takko session**. With that enabled, clicking Apply in Takko should be sufficient, without a second click on every operation in the plugin. Trust must be bound to the paired local app, Studio session and selected place, and reset on reconnect. Keep playtest initiation explicit. This trust flow is proposed, not present in the current plugin.

When the place is in Play mode, say **Stop testing to apply changes**. If the user edited affected objects, say **Your Studio edits need review** and preserve them. If a receipt is lost, show **Checking whether changes were applied** and reconcile before offering another apply. Convenience must not produce duplicate imports or overwrite user work.

## Why this is feasible

Roblox exposes `SerializationService:DeserializeInstancesAsync(buffer)` in Studio plugin context. It reconstructs instances from native RBXM bytes, without a user-facing file import. Its companion serializer produces the bytes. The official documentation cautions that the binary format itself has no stability contract for third-party parsing, so use Roblox-generated bytes and Roblox's reader rather than writing a custom model parser. [Official API](https://create.roblox.com/docs/reference/engine/classes/SerializationService), [official detailed source](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/SerializationService.yaml).

Takko already does this during component capture and adaptation. `src/generation/component-archive.ts` serializes the root, retains the binary and manifest, deserializes a copy, and compares observable properties and references. `component-adaptation.ts` binds the final adapted archive to the reviewed source chain. The remaining gap is sending that approved binary to the plugin's final apply path.

Current `bridge.ts` explicitly rejects native components in both enqueue and current-project validation. Its poll response contains generated bundle data and mesh IDs, but no native component transfer. `plugin/Forge.plugin.luau` creates the generated scene and scripts in staged roots, then swaps them into the owned namespace. It has no native component receiver. Removing the rejection alone would silently omit content.

This recommendation does not require adding Rojo live sync. The existing Rojo conversion can remain for optional place downloads. Removing its role from component preparation itself is separate work because current integration acceptance also checks the converted XML. Deliver the retained native archive first without weakening that existing acceptance chain.

## Concrete implementation boundary

| Area | Required change |
| --- | --- |
| Accepted component loader | Resolve the final reviewed adaptation archive using the existing integration record and adaptation-chain validators. Never send the original unrestricted archive merely because it is available. |
| Delivery identity | Create a delivery digest covering the generated artifact, ordered component archive hashes, integration record hashes and destination paths. Bind operations, applied state and test receipts to it alongside the existing revision and dispatch identity. A bundle-only hash does not identify native content. |
| Bridge protocol | Add an explicit native-component capability. Older plugins get an actionable update message. Keep the native-content guard for incompatible plugins. |
| Transfer | Serve bounded chunks through the existing authenticated local bridge, scoped to the dispatched operation and component. Verify chunk indices, lengths and whole-content hashes. Bound total delivery size and instance count as well as individual archives. Never expose arbitrary local file paths. |
| Plugin staging | Decode the archive with EncodingService and deserialize it with SerializationService outside the live data model. Check root count, destination, hierarchy/source inventory and retained sandbox/capability state. Keep every root tracked for cleanup if validation fails. |
| Placement | Attach the complete component under its accepted `Workspace/<scope>/Assets/<need>` destination. Preserve its root name and internal instance references. Resolve allowed generated references after native staging. Reject overlapping generated declarations. |
| Commit and recovery | Recheck Edit mode, operation validity and ownership after yielding downloads/deserialization. Commit only after all components and generated content stage successfully. Extend change detection, undo and receipt reconciliation to the native roots. Do not automatically replay an uncertain mutation. |
| UI | Replace export-first guidance with the selected-place status and Apply action only when the plugin advertises the capability. Display real progress and errors. Keep asset access and apply/test readiness distinct within the Studio panel. |

Roblox's EncodingService already provides Base64 decoding and hashing for the receiver. The current adapter's bounded chunk transfer is a reusable starting point, although its receiver runs on the host today. [Official EncodingService API](https://create.roblox.com/docs/reference/engine/classes/EncodingService).

MCP Studio IDs and custom plugin session IDs remain separate. Sending to the selected plugin session avoids pretending these IDs match. Asset operations can retain their explicit MCP target until there is a reliable identity handshake. This is a reason to simplify the presentation while preserving capability-specific state internally.
