# Chat part 4

Part 4 implements the chat status strip, sequential inline proposal questions, persisted build messages, step retry cards and desktop composer layout. Fresh prototype click-through was blocked by the browser tool's URL policy. Full visual parity is not established.

## Changes

- The project header shows its name and active preset, builder model and spending cap. The preset opens Models. The status strip has one state and cumulative spend. Building also shows task progress, elapsed time and Stop. The composer has a second Stop control and remains editable.
- Proposal questions, including R6/R15, use one inline question at a time with a recommendation, Other, Back and Next. Answers become receipts. Plans show three plain bullets before asset needs. Build estimates use historical builder calls when available. With no relevant history, the UI says the estimate is unavailable rather than inventing a price.
- Messages submitted during work are persisted in project JSON with idempotent submission IDs and conversation receipts. Worker checkpoint saves merge newly received queue entries. At the next dispatch boundary, completed output is kept and the queue receives one planner edit within the existing allowance. Applied means applied to the saved plan. Building requires another explicit approval.
- Stop and failures hold messages. Recovery never replays queued or partially applied work automatically. Changed revisions are held for review. Budget rejection holds the edit without dispatch. Queued or held messages can be removed. Messages arriving during a plan edit are held if that edit changes their context.
- Ready to test has export and a short Studio checklist. Failed and Stopped cards show kept work, historical cost and explicit retry or Continue when a valid checkpoint exists. Technical details are collapsed. Old conversation cards cannot change the current run. Source inspection remains available.
- Planning retry still stops at plan review. Later worker retries reuse the existing generation cap, approved proposal and durable task checkpoints. An offline incremental-build regression retries only the failed HUD worker, keeping completed replacements.
- The full persisted conversation reaches planner calls. Attachment and natural-language browser tests use the actual message API and a mocked planner contract.
