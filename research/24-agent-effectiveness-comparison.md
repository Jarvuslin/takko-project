# Which agent systems are more effective?

September 16, 2026. This supersedes the earlier presumption that Takko's current core should be retained. Existing implementation is not evidence of superiority. Replacement, embedding an external agent, and selective adaptation are all valid outcomes of a comparison.

## First direct result

OpenCode 1.18.31 and the current Takko Engine were run against three identical, authored pure-Luau component tasks using `openai/gpt-4.1-mini` through OpenRouter. Both passed all public acceptance tests. OpenCode cost less; Takko finished faster. This is an actual external CLI run, not a reimplementation of OpenCode's design.

| Harness | Passed logic tasks | Provider calls | Model cost, all three | Mean elapsed/task | Input tokens | Cached input tokens |
|---|---:|---:|---:|---:|---:|---:|
| Takko | 3/3 | 6 | $0.0243528 | 9.28 s | 50,062 | 1,920 (3.84%) |
| OpenCode 1.18.31 | 3/3 | 14 | $0.0156412 | 25.06 s | 82,855 | 72,576 (87.60%) |

OpenCode was **35.8% cheaper** in these runs and approximately **2.7 times slower**. Total experiment spend was **$0.039994**, confirmed both by all twenty response receipts and by the settled provider key-usage increase. Neither harness needed a manual code repair. OpenCode performed three completed `write` calls and three completed public-test `bash` calls; its transcript also retains one failed read. Takko used its normal builder and reviewer for each task and delivered `ready_to_test` artifacts, which were then independently executed by the offline evaluator.

The cost finding is specifically a **cache advantage**, not fewer tokens: OpenCode sent about 65% more input tokens. Repricing the same token counts with no input-cache discount would yield approximately $0.037415 for OpenCode and $0.024929 for Takko. That is a counterfactual arithmetic comparison, not another experiment. The append-and-reuse interaction pattern is a plausible explanation for the observed cache difference, but prompt layout was not separately randomized or ablated, and cross-request cache state was not controlled.

## What the pilot tested

- Crunch state: count after completion, exact deadline, rejected overlap, duplicate completion, cancelled/stale tokens, reset and independent controllers.
- Combat state: combo cycle, cooldown, reset boundary, rejected-input timing, per-target hit deduplication, new-swing hits and reset.
- Checkpoint state: ordered progress, rejected skips/invalid indices, duplicate finish, respawn retention, restart and independent courses.

Both received the same natural-language requirements and the exact public Luau assertions. The authored specification and API names were frozen evaluation inputs for both; this is not autonomous game planning. The algorithms were generated by the respective workers. OpenCode could read/write its isolated project and execute the supplied check command; Takko retained its production structured builder/reviewer workflow. Thus this compares the **configured systems, including their different tool affordances**, rather than isolating a single prompt or loop change.

An admission proxy enforced the selected model, output bounds, at most twelve requests per run, a $0.15 per-run ceiling and a $1 aggregate ceiling. Input reservations used request byte counts conservatively; unsettled calls retain their liability. All calls settled. OpenCode received a dummy local-proxy credential, not the provider key. Separate temporary workspaces prevented it from inheriting this repository's instructions or editing Takko. External plugins, other providers, delegation and unrelated commands were disabled. CLI startup/dependency initialization is included in elapsed times; installation itself is excluded.

**Limits:** one run per harness per task; deliberately small components; public tests; a single cheap model; no held-out generalization test; no Marketplace search, imported assets, animation, audio, replication or Studio operations. Six passing component tests do not establish that either system makes better games. The pilot favors cheap screening before spending on difficult integration comparisons, and does not resolve the user's main Marketplace question.

## Useful external controlled evidence

GitTaskBench evaluates reuse of existing repositories across 54 tasks. Its table 3 reports, with GPT-4.1: Aider 7.41% task pass rate at $0.0355 reported cost, SWE-agent 31.48% at $0.661, and OpenHands 42.59% at $0.942. The authors average two runs under their settings. These historical configurations show that the agent environment can materially affect outcomes with the same model, and that the cheapest attempt need not be the most effective. They do not compare current Takko or Roblox. [Paper and configuration appendix](https://arxiv.org/html/2508.18993v1), [authors' code](https://github.com/QuantaAlpha/GitTaskBench).

Aider's 2024 architect/editor experiment reported 85% with o1-preview plus an editor on its editing benchmark. It supports separating reasoning from edit formatting in that setting, not adding another model call to every task. [Original experiment](https://aider.chat/2024/09/26/architect.html).

mini-SWE-agent's public documentation and SWE-bench leaderboard show substantial coding capability with a small control loop. Scores depend on the accompanying model and configuration. This is evidence against assuming that additional orchestration necessarily improves results. [Agent documentation](https://mini-swe-agent.com/latest/), [benchmark maintainers' leaderboard](https://www.swebench.com/).

OpenHands publishes benchmark infrastructure and traces for broader software-engineering evaluations. That makes it a testable replacement candidate; its index primarily compares models within its environment, so it cannot by itself rank OpenHands against Takko. [Benchmark code](https://github.com/OpenHands/benchmarks), [index methodology discussion](https://www.openhands.dev/blog/analyzing-and-improving-openhands-index).

## Decision after this evidence

1. Keep **OpenCode and OpenHands eligible to replace the worker execution layer**, not just as sources of small ideas. OpenCode has a measured local cost advantage in the narrow pilot; OpenHands has relevant external repository-reuse evidence.
2. Include **mini-SWE-agent as the simplicity baseline**. If it performs as well, avoid maintaining unnecessary orchestration.
3. Test **Aider or Cline specifically for repair**, where their editing interfaces are most directly relevant.
4. Make the next expensive comparison resolve the real uncertainty: can the worker discover a suitable complete Marketplace component, inspect its behavior/dependencies, integrate it and satisfy native acceptance tests without root rescue? Use equivalent Studio capabilities for a loop comparison, then separately compare end-to-end products with their best supported tools. Do not force every candidate through an existing Takko limitation and call that a fair test of its own capabilities.
5. Choose using native success rate, total cost including failed attempts, elapsed time and intervention rate. If an external worker wins consistently, adopt it even when that retires existing Takko code. If the gain is isolated to cache behavior, a smaller request-layout change may achieve it more economically. Both possibilities remain open.
